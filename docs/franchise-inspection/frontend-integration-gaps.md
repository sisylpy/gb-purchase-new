# 巡店与整改小程序前端联调缺口

记录时间：2026-08-04

本文只保留对当前 Controller、DTO、Service、SQL 和前端调用实现逐项核对后仍存在的缺口。前端未修改后台，也未用固定 ID、固定 Token、mock 或本地角色伪造正向结果。

## 一、当前入口阻断：角色主权尚未收口

原有门店用户角色是 `gb_department_user.gb_du_admin` 单值；巡店后台另外从 `gb_fr_user_role` 和 `gb_fr_user_store_scope` 读取多角色与门店范围。`/franchise/v1/me` 只读后一套。详细证据见 `role-registration-audit.md`。

后台当前没有“当前登录用户追加巡店员角色”的既有统一合同。前端已删除先前猜测的 `PUT /franchise/v1/me/roles/INSPECTOR`，不会用写入新角色表的接口掩盖双重主权。

最小后台需求是：先确定统一角色主权，然后提供一个幂等的当前用户追加角色能力；用户由现有 Token 识别，不接收前端用户、品牌、部门或门店 ID，不创建第二用户，不覆盖已有角色和组织关系；成功后 `/franchise/v1/me` 必须从同一主权返回新角色。在后台确认 URI 和 DTO 前，前端不再推测接口名称。

## 二、影响幂等验收的命令合同

1. `POST /franchise/v1/inspections` 只接收 `storeId`、`startedAt`、`summary`，没有 `idempotencyKey`，后台也没有创建巡店单的幂等记录。前端已禁用连续点击，但无法保证网络超时后重试不生成第二张巡店单。
2. `POST /franchise/v1/rectification-tasks/{taskId}:accept` 只接收 `rowVersion`，没有 `idempotencyKey`。前端已禁用重复点击，但无法完成“接受任务同键同请求返回原结果”验收。
3. 确认问题、创建整改任务、提交巡店、提交整改和复核已有 `idempotencyKey`；前端对这些命令持久化完整请求，重试使用原键和原请求。

## 三、现场原文修订合同

巡店记录只有新增接口，没有更新或作废已保存原文的接口。如果已保存记录还没有照片，前端可新增一条修订记录；如果已有照片，因照片必须关联真实 `inspectionItemId`，必须先作废旧照片并在新记录重新上传。

AI 失败会将当前记录的 `rowVersion` 递增并保存失败码。前端已在 422 后重新读取最新记录，保留原文、已上传照片和未正式提交的候选编辑。

## 四、问题与整改任务的首期约束

`POST /inspections/{inspectionId}:submit` 要求本次巡店的每个正式问题都已生成整改任务。因此当前合同不支持“确认正式问题但不生成整改任务”。前端将候选项明确表达为“确认该问题并生成整改任务”；不勾选的候选不会生成正式问题或任务。如产品后续要求问题可不带任务，需先调整后台提交规则。

## 五、多角色任务范围冲突

整改任务列表和详情的当前后台判定存在多角色冲突：用户只要同时具有店长角色，非总部范围的列表就会强制按“负责人是本人”过滤；详情也会先套用“店长只能查看分配给本人的任务”。这会阻止同时具有巡店员和店长角色的用户查看“复核人是本人、但负责人是其他店长”的待复核任务。该问题必须由后台按动作权限合并范围，前端不能绕过。

## 六、可降级展示但不伪造的数据缺口

1. `GET /stores` 仅返回门店标识、名称和运营部门标识，没有地址、区域、最近巡店和未完成标识。前端仅用正式巡店查询计算后两项，不伪造地址或区域。
2. 巡店、问题、任务和时间线主要返回操作人标识，只有当前用户和目标门店店长目录可转成真实姓名。其他人员展示“信息暂无”，不在页面暴露内部 ID。
3. 任务视图没有 `overdue` 字段。前端额外调用后台 `overdue=true` 列表，以后台返回的任务集合标注逾期，不用手机时间修改状态。
4. 媒体列表响应不包含业务关系，接口也不能按 `businessType`、`businessId`、`mediaStage` 过滤。前端可从 AI 候选、整改提交和复核响应中恢复已引用的媒体；如果应用本地数据被清除且现场照片尚未被 AI 候选引用，就无法从后台精确恢复“属于当前巡店记录”的照片。
5. 时间线只提供通用 `detail`。整改提交和复核照片可用 `submissionId` 或 `reviewId` 从详情映射；其他事件没有独立相关媒体字段。
6. 8090 实测中，业务鉴权失败由统一响应体返回，但媒体路径参数不能转换为数字时，会在进入 Controller 前返回原始 Spring 400 响应并包含完整堆栈。前端能将其归一化为失败，但后台仍应用全局异常处理统一错误包络并关闭堆栈外泄。

## 七、当前环境联调条件

命令行无法获取微信开发者工具 Storage 中的正式登录态，当前也没有可供联调的正式巡店员和店长账号。因此可以完成 8090 连通、匿名、无效 Token 和无数据变更的负向合同检查；注册、门店范围以及完整正向闭环必须等统一角色合同和正式测试账号就绪后在微信开发者工具中继续。

## 八、前端已实施的合同内保护

- 正式提交只使用状态为 `READY` 的 `mediaAssetId`；微信临时路径不进入本地持久草稿或业务命令。
- 列表完整分页后按正式主键去重；快速切换标签时用请求序号防止旧响应覆盖新页面。
- 列表失败保留已有数据并显示可重试错误，不把 403、500 或断网显示成空列表。
- 401/403 鉴权失效复用现有微信登录刷新；404、409、422、500、网络超时、上传失败和空列表都有独立处理，不回退到 mock 数据。
