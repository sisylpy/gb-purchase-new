# 巡店与整改小程序前端联调缺口

记录时间：2026-08-04

以下内容来自正式 `backend-api-contract.md`、后台响应模型和小程序接入实现。前端未修改后台，也未用固定 ID、mock 或本地状态伪造缺失能力。

## 阻断或影响正式验收的接口缺口

1. `POST /franchise/v1/inspections` 的正式请求只有 `storeId`、`startedAt`、`summary`，没有 `idempotencyKey`，后台也没有创建巡店单的幂等记录。前端只能在一次页面会话内禁用重复点击，无法保证网络超时重试不生成两张巡店单。
2. `POST /franchise/v1/rectification-tasks/{taskId}:accept` 只有 `rowVersion`，没有 `idempotencyKey`。前端已禁用重复点击，但无法按产品要求验证“接受任务”同键重试。
3. 巡店现场原文只有新增接口，没有更新或作废巡店记录接口。AI 返回 422 后，前端只能新增一条修订记录；如果原记录已有照片，必须先作废并在新记录下重新上传，不能直接“修改原始记录后重试”。
4. 当前运行环境没有可用的巡店员/店长微信正式登录态。不能用开发 Header、固定用户 ID 或验收历史 ID 代替，因此小程序页面上的正向真实闭环需要具备正式角色的微信用户登录后继续验收。

## 可降级展示但不伪造的数据缺口

1. `GET /stores` 仅返回 `storeId`、`storeName`、`operatingDepartmentId`，没有地址、区域、最近巡店时间和未完成标记。前端通过正式巡店分页接口计算最近巡店与未完成状态；地址/区域明确显示“后台未提供”。
2. 巡店、问题和任务视图主要返回用户 ID，没有巡店员名称和时间线操作人名称目录。当前登录人和门店店长可显示真实名称，其余操作人显示“用户/巡店员 + ID”。
3. 任务视图没有 `overdue` 字段。前端额外调用 `overdue=true` 的正式任务查询，将后台返回的任务 ID 标记为逾期，不使用手机时间自行判断。
4. 问题详情和任务详情没有直接返回巡店问题的现场媒体列表。首期巡店问题通过 `candidateKey` 回查巡店记录中的 AI 候选 `evidenceMediaIds`；总部手工问题无法用该方式恢复现场图片。
5. 媒体列表没有返回业务关系，也不能按 `businessType/businessId/mediaStage` 查询。上传成功后前端会把正式媒体对象保存在本地页面草稿中；如果上传完成后应用数据被清除、且 AI 尚未关联这些媒体，前端不能从后台准确恢复“属于当前巡店记录”的照片。
6. 时间线事件只返回操作人 ID 和通用 `detail`。整改提交/复核照片可通过 `submissionId`、`reviewId` 与详情中的媒体映射，其余事件没有独立的相关照片字段。

## 前端已采用的合同内处理

- 所有正式命令保存 `rowVersion`；要求幂等的确认问题、创建整改任务、提交巡店、提交整改、复核动作同时持久化完整请求与 `idempotencyKey`，网络重试复用完全相同的请求。
- 图片只用后台 `mediaAssetId` 进入业务提交；缩略图和原图通过带 Bearer Token 的下载请求获取临时展示文件。
- 上传中退出会把本地任务恢复为“上传已中断”，允许用户重试；上传未完成时禁止正式提交。
- 401/403、404、409、422、500、网络失败、上传失败和空列表均保留表单并显示明确状态，不回退到 mock 数据。
