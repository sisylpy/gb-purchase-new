# 巡店与整改小程序最终合同核对

记录时间：2026-08-05

核对基线：后台正式提交 `0ca55ab4074c9f25341c93a1ca724a03bad10e97` 及
`docs/franchise-inspection/backend-api-contract.md`。

## 已接入的最终合同

- 正式巡店员注册：`POST /franchise/v1/inspectors:register`，第一次微信 code 只使用一次；成功后以第二个
  code 调用现有 `gbLoginIndex/{code}`，再用新 Token 校验 `/franchise/v1/me`。
- 创建巡店：持久化 `idempotencyKey`、`storeId`、`startedAt`、`summary` 完整命令；失败或超时后原样重试，
  成功后才清除。
- 接受整改：持久化 `idempotencyKey + rowVersion`；失败后不自动换键。版本冲突时必须由用户明确确认，才会
  清除旧命令并基于新版本重新发起。
- 现场原文：已接入 PATCH 修改和 DELETE 审计作废。修改后立即清除本地旧候选，使用服务端新的检查项版本；
  作废后保留原文、原因和状态历史。
- 媒体：已接入 `INSPECTION`、`INSPECTION_ITEM`、`ISSUE`、`RECTIFICATION_TASK`、
  `RECTIFICATION_SUBMISSION`、`RECTIFICATION_REVIEW` 六类业务关系查询。
- 非数字媒体 ID：统一识别 `MEDIA_ASSET_ID_INVALID` 并显示“照片标识无效，请刷新页面后重试”，不展示堆栈。
- 角色：只使用 `/franchise/v1/me` 的正式角色与动作，不保留旧加盟角色表兼容和本地角色伪造。

## 仍需真实环境验收的项目

以下项目不能由静态合同检查代替，必须在微信开发者工具和两个正式微信用户下留下新业务记录后填写结果：

1. 巡店员注册、第二次登录、`/me` 的真实身份与门店范围。
2. 新巡店单、原文修改和作废、照片上传、AI 多候选编辑删除、正式问题和整改任务。
3. 店长接受、草稿、两轮提交，以及巡店员退回和最终通过。
4. 创建巡店和接受整改的同键同请求、同键不同请求及旧版本冲突。
5. 六类媒体关系、完整时间线和 iPhone 12/13 竖屏视觉检查。

## 当前最小合同注意点

- 正式用户角色是 `gb_department_user.gb_du_admin` 单值。巡店员和店长不能由同一用户兼任，真实闭环必须切换
  两个微信身份。
- 媒体关系查询返回读取所需的 URL、状态、顺序和阶段，但不返回媒体资产 `rowVersion`。刷新页面后可可靠展示
  业务照片；若产品要求在关系查询结果上直接作废媒体，后台还需补充媒体版本或按业务关系作废的正式合同。
- `/stores` 不返回地址或区域；页面只展示正式名称，并用巡店查询计算最近巡店和未完成标识。
- 时间线操作人姓名只从当前身份和正式门店人员目录解析；没有真实姓名时显示“信息暂无”，不暴露内部 ID。
